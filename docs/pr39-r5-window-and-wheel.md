# PR #39 r5 — окна и колесо мыши

## Воспроизведённое поведение

На собственной синтетической сессии Excel16/Win64 клик в ячейке книги-владельца оставлял конструктор видимым. После Ctrl+Tab на другую книгу он оказался позади её SDI-окна. Диагностическая функция показала `AtAdminMain/True`: форма и настройки не уничтожены. Простые Hide/Show существующей формы не устранили перекрытие при последующей активации другого окна. Это подтверждённый вариант причины, а не доказательство всех причин наблюдения владельца.

Ограниченное исправление: стандартные события [Application.WindowActivate](https://learn.microsoft.com/en-us/office/vba/api/excel.application.windowactivate) и SheetSelectionChange поднимают уже существующую форму в этой Excel.Application. `FindWindowW` ищет временно уникальный заголовок; PID проверяется против текущего процесса Excel, русский заголовок восстанавливается. [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos) использует HWND_TOP и SWP_NOACTIVATE|SWP_NOOWNERZORDER|SWP_NOMOVE|SWP_NOSIZE. Не меняются владелец окна, фокус, положение/размер и глобальный topmost-статус. Это не Windows hook и не subclass callback.

Приёмник Office создаётся только при открытом конструкторе; Close/QueryClose/Terminate освобождают ссылку. Во время InputBox выбора Range подъём приостановлен, включая активацию книги/листа; после выбора/отмены показывается прежняя форма. Повторный AtAdminOpen не пересоздаёт модель, форму и явный выбор книги. Если API отказывает, выводится сообщение о необходимости повторного открытия, успех не имитируется. Программно проверены фокус книги/ячейки, picker guard, singleton и отключение приёмника; настоящими кликами — переключение книг и возврат после выбора названия. Нативные ресурсы Windows с обратными вызовами не регистрируются.

## Колесо: явно неподдержанная возможность r5

В [перечне событий MSForms](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/events-microsoft-forms) нет MouseWheel. На итоговой r5 ввод колеса над вложенным полем не сдвинул содержимое; штатные ↑/↓ и полоса сдвинули его. Утверждать поддержку произвольного наведения или всех вложенных контролов нельзя.

Рассмотрен ограниченный subclass окна, а не глобальный перехват. Но [SetWindowSubclass](https://learn.microsoft.com/en-us/windows/win32/api/commctrl/nf-commctrl-setwindowsubclass) хранит адрес callback без reference counting и требует снятия тем же адресом/ID. [VBA End](https://learn.microsoft.com/en-us/office/vba/language/reference/user-interface-help/end-statement) обрывает исполнение без событий завершения. Вывод для этой архитектуры: гарантированное снятие VBA callback при reset/End не доказано; риск висячего адреса и падения Excel неприемлем. Scoped Windows subclass/hook, глобальный hook и polling-таймер не добавлены.

**Решение r5:** явное ограничение и безопасная альтернатива — нативная вертикальная полоса плюс ↑/↓, доступные через Tab/Enter и существующие только при переполнении. Внешних оконных обработчиков после закрытия нет. Это не выполнение требования о прокрутке колесом; используется прямо разрешённый заданием fallback. Полноценная wheel-поддержка потребует отдельно доказанного жизненного цикла, включая reset, закрытие, вложенные HWND и отсутствие прокрутки листа; возможный native-компонент нельзя добавлять как косметический обход без отдельного решения. Переход на XLAM сам по себе проблему не решает.

## Границы подтверждения

Фактический DPI Windows не менялся. Проверки геометрии480×300pt, видимого перекрытия/подъёма и отдельный ввод колеса не заменяют ручную приёмку125/150/200%, всех вариантов фокуса, других приложений или Office x86. Требования безопасности Writer не менялись; оконный приёмник не читает/не пишет значения заявок и не влияет на вычисления или журнал.
