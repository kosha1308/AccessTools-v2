# PR-07 — первый редактор и сквозной запуск

**Статус: частичный сквозной сценарий, требуется ревью ограничения Writer и ручная приёмка UI.** База `281d57d9badba6df8fa7da7e3d546d59cf85e355`, ветка `feat/pr-07-admin-vertical-slice`. PR-08 не начат.

Реализованы настоящие диалоги Excel: открытая книга → лист → выбор ячейки → название поля Text → «равно тексту» → сообщение, серьёзность, RGB-цвет и явный выбор Note. Пользователь не редактирует AST/XML/VBA. Это один пошаговый редактор одного независимого скалярного правила; полного конструктора, распознавания шаблонов, публикации и ролей нет. Интерфейс прототипа англоязычный, цвет задаётся RGB-числом Excel.

## Запуск и ручная приёмка

В Windows с Excel собрать отдельную синтетическую книгу запуска:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools/Build-AdminDemo.ps1 -OutputPath C:\SafeLocal\AccessTools-Admin.xlsm
```

Каталог должен существовать, файл назначения — отсутствовать. Сборка импортирует только `src` в собственную новую книгу Excel. Доступ к VBA Project должен быть уже разрешён окружением; скрипт не меняет настройки безопасности. Использовать обычные правила доверия макросам своей организации, не отключать защиту для демонстрации. Данные и конфигурации в репозитории исключительно синтетические.

1. Открыть собранную `.xlsm`, отдельно создать тестовую книгу с листом `Request`, значением `wrong` в `B2` и формулой `=1+2` в `C2`. Для Notes сохранить тестовую книгу как `.xls` в доказанном профиле; для заливки — `.xlsx`.
2. Нажать **Open editor**, ввести **NEW**. По номеру выбрать целевую открытую книгу, ввести имя листа, мышью выбрать одну ячейку, указать имя поля и ожидаемый текст `expected`.
3. Указать сообщение, `ERROR` / `WARNING` / `INFO`, цвет (`255` — красный, `65535` — жёлтый), `Add Note=false` для `.xlsx` или явно `true` для `.xls`. Отмена любого шага оставляет прежнее определение.
4. **SAVE** сохраняет XML в новый файл (существующий не перезаписывается), затем **CLOSE**. Заново открыть редактор, **LOAD** сохранённый XML, **RUN**, явно выбрать книгу и безопасный локальный родительский каталог нового журнала. Книга запуска должна оставаться открытой до очистки отметок.
5. Проверить FAIL и отдельно статус записи. В `.xlsx` появляется заливка, в поддерживаемом `.xls` — заливка и Note с `AccessTools`, уровнем и сообщением. Повторный RUN не создаёт дублей. Значения и формулы не меняются.
6. Не меняя входную ячейку, выполнить **CLEAR**: свои отметки удаляются, исходное оформление возвращается; после успешной очистки можно выбрать другую книгу. Журнальные файлы автоматически не удаляются.
7. Через **EDIT** изменить ожидаемый текст, сообщение, цвет или выбрать новую координату; **SAVE** в новый файл, **LOAD**, **RUN**. Логические FieldId и RuleId остаются прежними. Адреса в коде не менять.
8. Проверить `PASS ↔ FAIL`, меняя значение книги. Пустота, число при объявленном Text и отсутствующий лист должны давать `CANNOT_EVALUATE`, а не PASS. Не завершённый расчёт сохраняет прежние отметки.
9. В `.xlsx` явно включить Note и получить `CAPABILITY_UNSUPPORTED`, без скрытой замены на одну заливку. Проверить сохранность пользовательских данных, формул и примечаний.
10. **Обязательно проверить ограничение ниже:** FAIL с нанесённой отметкой → изменение значения этой ячейки на PASS. Условие стало PASS, но очистка сообщает `CONFLICT/TARGET_CHANGED`; отметка остаётся. Это ожидаемый отказ защиты, а не успешная полная обработка.

**Ручное нажатие кнопок и прохождение диалогов не проверено.** Сборка `.xlsm`, импорт/компиляция исходников и программный сквозной API проверены отдельно; они не доказывают удобство или работоспособность всех интерактивных переходов.

## Контракты и совместимость

`AtAdminDefinition` строит обычные Template/Locator/Field/Expression/Rule/Action, без процедур для определённого шаблона. Text equality — существующий `OP_TEXT_EQUAL@1.0.0`, `MODE=binary`, строгая регистрозависимая проверка. Другие AST этот небольшой редактор отклоняет целиком, не переписывая их под свой профиль.

Цепочка: явно выбранный Workbook → существующий `AtNewExcelResolver` → immutable `CAtEvalContext` → существующий Evaluator → `AtEvaluateRule` → `CAtRuleOutcome` → `AtOutcomeIntents` → существующие Planner/Writer. Ни Evaluator, ни Resolver не пишут в книгу.

`RuleOutcome` содержит RuleId, исходный EvalResult с диагностикой/requirements/provenance и статус. Только `IsComplete=True`, `ResultType=Bool`, канонические `true`/`false` дают PASS/FAIL. Всё остальное — CANNOT_EVALUATE; материализация действий для него запрещена. FAIL создаёт готовые ActionIntent по ссылкам Action → Field → A1 Locator. PASS создаёт пустой набор для сверки предыдущих собственных отметок. Это запуск одного правила и полного набора его отметок в отдельном журнале, не многоправильный scheduler; нельзя делить такой журнал между независимыми запусками других правил. Не реализованы зависимости исполнения правил и сложная маршрутизация результатов.

XML **SchemaVersion=3.0.0** использует прежний namespace и прежний AST 2.0.0. Только для Action добавлены обязательные `OnOutcome=FAIL`, `Message`, `FillColor` (каноническое целое 0–16777215), `AddNote=true|false`; требуется ровно один Field target. Прежние Trigger/Audience/Channel сохранены: Trigger Error/Warning/Info задаёт серьёзность, Audience — Initiator/FirstLine/Coordinator, Channel — Results для заливки либо Comment для заливки с Note. Approval/Report этим профилем не исполняются. Длина сообщения проверяется вместе с заголовком и уровнем Writer (512 символов всего).

Схемы 1.0.0 и 2.0.0 читаются и валидируются в прежнем смысле; новые свойства там запрещены. Схема 1 остаётся неисполняемой; AST схем 2/3 исполняется существующим Evaluator. Автоматического апгрейда нет. Старый loader откажет на 3.0.0. Существующий тест неизвестной схемы использует 99.0.0 вместо теперь поддерживаемой 3.0.0. Пример: [admin-equality.xml](../tests/fixtures/admin-equality.xml).

## Ограничение, препятствующее полной приёмке

Writer PR-06 сравнивает полный ожидаемый снимок, включая данные/формулы целевой ячейки. **Обычное редактирование помеченного входа меняет этот снимок:** даже если изменились только входные данные, Writer запрещает замену или очистку как `CONFLICT`. Это воспроизведено в настоящем Excel и для заливки, и для Note. Интерфейс сохраняет независимо вычисленный PASS и показывает неполный output; не сообщает, что отметка успешно снята.

Защитные проверки Writer не ослаблены, пользовательские значения не восстанавливаются ради обхода конфликта. В тесте исходное синтетическое значение возвращается явно самим тестом только для отдельного доказательства штатной очистки неизменённой области. Это **не** автоматическое восстановление и не предлагаемый рабочий обход.

Нужно отдельное решение владельца о будущем контракте Writer: как доказанно различать разрешённое редактирование входных данных и конфликт с собственными свойствами отметки. До такого решения нельзя объявлять полностью готовым сценарий автоматического снятия отметок после исправления заявки. Возможен и конфликт при изменении координаты, если прежняя помеченная область уже была изменена пользователем.

Остальные ограничения PR-06 сохранены: Notes только `.xls` / Excel 16.0 build 17932 Win64; `.xlsx` — заливка без Notes; ограниченные стили/объединения; отказ на неподдерживаемых свойствах, protection, пользовательских Notes/threaded comments. Внешний журнал в новой выделенной локальной папке, владение только в живой сессии, никаких автоматических попыток recovery/rebinding после её потери. Полной транзакционности нет. См. [контракт Writer](pr06-excel-writer.md).

## Проверка

**501 PASS, 0 FAIL = 458 прежних +43 новых**, Excel 16.0 build 17932, Office x64 / Windows x64. Воспроизведение: `tests/Run-Tests.ps1`; evidence `artifacts/run-ef16d4ef4c5f480281813aa3977a8c7b` (host, source hashes, шесть result-файлов, `admin-assertions.txt`, worker exit 0). Новый suite проверяет сохранение/загрузку/исполнение, изменение условия и координаты с прежними ID, PASS/FAIL/неполноту, Unicode/цвет, строгую схему, Writer envelope, нанесение/повтор/штатную очистку, конфликт после редактирования данных, сохранность значений/формул и отказ Notes в `.xlsx`. Полный `.xls` профиль заливка + Note проверен программно.

Два прежних native API случая Writer остаются UNVERIFIED; Office x86, ручная приёмка UI и recovery после гибели процесса не проверены. Runner дополнен новым suite и удержанием process handle для надёжного чтения ExitCode Windows PowerShell; ошибка теста по-прежнему завершает запуск с ненулевым кодом.
