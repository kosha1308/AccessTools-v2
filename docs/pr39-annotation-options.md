- В самом `modAnnotations` нет внешнего журнала владения или файлов снимков; метаданные находятся в книге. Это не утверждение, что вся v1 не создавала файлов: итоговые Superset-книги, конфигурации, кэш и логирование описаны отдельно в [аудите вывода](v1-excel-output-contract.md).

Риски v1: изменение CF priorities, неполная сохранность исходного оформления/Notes, ошибочное узнавание владения по строке/цвету, осиротевшие CF после удаления Note, неоднозначность разных адресов одной MergeArea, подавление ошибок. Сначала очищались старые отметки, поэтому сбой проверки мог оставить книгу без прежних результатов. Удобный пользовательский сценарий не доказывает безопасность реализации.

## Сравнение вариантов

| Вариант | Безопасность / надёжность | Сложность / ограничения |
| --- | --- | --- |
| Повторить v1: CF + metadata Note | Не доказана при конфликте/потере metadata; нельзя узнавать владение по цвету/тексту | Просто для пользователя, но CF priorities/merge/Notes требуют нового Writer и испытаний |
| Только память сессии | Можно ограничить изменения живой сессией, но теряется write-ahead evidence при прерывании | Проще, но регресс гарантий и новая политика recovery |
| Журнал внутри книги | Меняет структуру/метаданные и Saved, требует сохранения книги; проблемы readonly/несохранённых книг | Существенная архитектурная переработка, не косметическая задача |
| Внешний журнал с ручной папкой | Сохраняет доказанное владение и fail-closed | Неприемлемый технический диалог и мусор для обычного сотрудника |
| **Тот же журнал, автоматическая оболочка** | Сохраняет Writer guards; законченные журналы удаляются только по подтверждённому владению | Минимальное расширение жизненного цикла, без нового формата и без автоматического crash recovery |

## Выбранная рекомендация в этом PR

Не заменять Writer. Убрать выбор папки из административного сценария; создавать собственную уникальную папку под `%LOCALAPPDATA%\AccessTools\Journals`. Автоматическая уборка допустима только для созданной текущей оболочкой папки текущей живой сессии, когда все записи ROLLED_BACK, recovery не требуется и все файлы/содержимое совпадают с известным manifest журнала. Удаляются только точные проверенные файлы и затем пустая папка; неизвестные файлы, вложенные папки, изменённые записи, конфликт и незавершённые операции блокируют уборку.

Успешная запись FAIL остаётся активным владением — её журнал нельзя удалять. После подтверждённой очистки/PASS журнал автоматически освобождается; после конфликта остаётся. Нельзя молча удалять по возрасту или автоматически принимать оставшийся после гибели Excel журнал за новый. Такие остатки сохраняются для разбора. Поэтому гарантируется отсутствие накопления **завершённых журналов нормальной живой сессии**, а не бесконечная уборка всех аварийных остатков. Квота/retention для аварийных данных — отдельная административная политика, не потеря доказательств ради чистой папки.

Безопасность удаления — read-only manifest проверки из `CAtOwnershipJournal`, без изменения планирования, записи, сравнения данных/владения или recovery. Для тестов корневой каталог задаётся явно под синтетической рабочей папкой; пользовательский путь не выбирается через UI. Существенную переработку формата/хранения Writer в этом PR не выполнять.

Будущий рабочий режим «Проверить заявку» должен единой командой выполнять resolve/evaluate/reconcile/apply; административный preview остаётся read-only, apply — явным. Эта оболочка и общий вход конструктора подходят для будущего Ribbon callback `.xlam`; сам рабочий режим, Ribbon и публикация здесь не создаются.
