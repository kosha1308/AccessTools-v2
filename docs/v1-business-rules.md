# AccessTools 1: реестр бизнес-правил

## Границы доказательства

Аудит исходников, не протокол запуска Excel. Исторический baseline: `main` d9aa9b88f9193c0d2935d99c5cc8ecca3865687c (15 dispatch checks). Последняя рабочая integration по заданию: 58d8789d1e60860c96cb35ba0e780a6424510130 (17 checks). Ссылки ниже фиксируют коммит, функцию и строки. Состояние рабочей книги правил пользователя неизвестно: итоговый текст, severity и аудитория могут переопределяться каталогом проблем. Наличие процедуры regression не является доказательством её выполнения.

Доказательства: CODE — семантика прямо восстанавливается из исходника; CONFIG — результат зависит от внешней книги/настройки либо есть конфликт baseline/ТЗ; UNVERIFIED — выполнение/реальная приёмка не подтверждены. Во всех правилах ручная приёмка Excel: UNVERIFIED / не выполнена. Классификация реализации A/B/C приведена отдельно в матрице: A декларативная, B составная, C специализированная операция.

## Общий контракт для 19 аспектов каждого правила

Следующие аспекты применяются ко всем карточкам вместе с их индивидуальными исключениями: (1) цель; (2) условие запуска; (3) входные значения и типы; (4) FieldId/locator; (5) источник; (6) успешный исход; (7) негативный исход; (8) EMPTY; (9) MISSING; (10) INVALID; (11) приоритет/исключения; (12) точный текст; (13) severity; (14) аудитория; (15) адрес подсветки; (16) примечания/общий writer; (17) повторный запуск/дедупликация; (18) дополнительные выходы/Superset/сводка; (19) тестовый вектор/состояние переноса/ручная приёмка.

Успех без issue — PASS, а не отдельное сообщение. `FinalizeCheckResult` выбирает ERROR > WARNING > INFO > PASS; `SkipCheck` сохраняет SKIPPED, счётчики и причину. RegisterIssue добавляет модель с CheckId, Severity, Field, Message, InstructionUrl, SheetName, Address и UiGroupKey/Label; не пишет в Excel. NoCell имеет пустые SheetName/Address. Общий pipeline позже применяет каталог, audience, маршрутизацию и аннотации; поэтому указанный в карточке literal severity — базовый, не гарантия финального оформления. Точные literal сообщения каждой result-producing точки приведены в приложении с контекстом условия. Динамические функции сообщений указаны там же; фактические параметры внешнего Rulebook не подтверждены.

Адрес задаётся `NetworkFieldRange` либо `CellArea`/сохранённой строковой ссылкой, а не фиксированным A1. Физические координаты зависят от найденной формы и MergeArea. Источники отсутствуют лениво: отсутствие файла не равно EMPTY. Повторный полный запуск сбрасывает config/field/extractor/result-view/registry-context/coordinator caches. Сам по себе RegisterIssue не дедуплицирует; локальные словари, перечисленные ниже, устраняют только отдельные повторы. Повторяемость аннотаций и сохранность пользовательских данных требуют ручной приёмки. Новая модель во всех карточках: ещё не реализована, документированный parity target; исполняемые правила v2 этим аудитом не создаются.

## Карточки 17 RuleId

<a id="nettemplate"></a>

### NET.TEMPLATE — CODE
Цель: предупредить о версии/структуре, продолжить известные проверки. Вход: текст заголовка и смысловые метки; источник template.ini CurrentTitle. Locator: FindCellStartsWith «Заявка на сетевую связность», строки 1–10; FindCellByText 13 меток до NetworkRequestLastRow. Отсутствие заголовка WARNING NoCell; несовпадение нормализованного заголовка WARNING MergeArea; отсутствующие метки собираются одним WARNING (titleCell либо NoCell). EMPTY title/неверная версия обрабатываются тем же сравнением; это не блокирующий отказ. Отдельного приоритета нет. Повтор меток агрегируется списком. Дополнительных выходов нет. Вектор: нет заголовка + нет IP источника => два предупреждения; правильная структура => PASS.

<a id="netrequired_fields"></a>

### NET.REQUIRED_FIELDS — CODE
Цель: обязательные ФИО, подразделение, должность, email. Вход: строки INITIATOR_FULL_NAME, INITIATOR_DEPARTMENT, INITIATOR_POSITION, INITIATOR_EMAIL. Locator NetworkFieldRange; внешних источников нет. Каждое MISSING поле WARNING NoCell, каждое EMPTY ERROR на поле, непустое произвольное значение принято; синтаксис ФИО/должности не проверяется. Все четыре условия независимы. Дедупликации между полями нет. Допвыходов нет. Вектор: пустые четыре поля => четыре ERROR; отсутствующая метка ФИО => WARNING.

<a id="netinitiator_email"></a>

### NET.INITIATOR_EMAIL — CODE
Цель: только синтаксис email, без допуска компании. Поле INITIATOR_EMAIL, строка Trim; regexp `^[A-Z0-9._%+\-]+@[A-Z0-9.\-]+\.[A-Z]{2,}$`, IgnoreCase. MISSING => SKIPPED, EMPTY => PASS (ошибка уже в required), INVALID => ERROR «Указан некорректный адрес электронной почты инициатора.» на email. Источников/допвыходов нет. Вектор a@example.ru PASS; a@b ERROR; пусто здесь PASS.

<a id="netinitiator_allowed"></a>

### NET.INITIATOR_ALLOWED — CONFIG
Цель: разрешённость email/домена. Email должен быть непустым и синтаксически корректным; иначе SKIPPED. RULEBOOK / «Инициаторы», LoadNetworkInitiatorRulesCached. MISSING файл/нечитаемый лист => SKIPPED; нет активных разрешающих строк => SKIPPED; хотя бы одна активная разрешающая строка совпала => PASS, иначе ERROR на email. Это закрытый список допуска: отсутствие совпадения здесь НЕ ALLOW. Условия содержатся в NetworkInitiatorRuleAllowsV2/MatchesEmailV2; нельзя заменять их новой regexp без parity. Вектор valid email вне существующего активного списка => ERROR. Внешние строки не предоставлены, фактический список не подтверждён.

<a id="netinitiator_approval_rules"></a>

### NET.INITIATOR_APPROVAL_RULES — CONFIG
Цель: дополнительные согласования для каждой активной совпавшей строки «Инициаторы» с непустым Approval. MISSING/EMPTY/INVALID email, отсутствующий файл, нечитаемый лист => SKIPPED. Нет совпадений => PASS. Все совпадения публикуются без остановки на первом. Сообщение «Для инициатора «{email}» необходимо добавить согласование: {Approval}.» + необязательный «Комментарий: {Comment}». Severity ERROR/ОШИБКА => ERROR; INFO/ИНФОРМАЦИЯ => INFO; остальное WARNING. Адрес email. Fallback IncludeInUserReport=False: видно в заявке, не ошибка инициатора; каталог «Проблемы» способен переопределить. Это важное исключение аудитории. Вектор две совпавшие строки => два результата (глобальная дедупликация не доказана).

<a id="netrequest_type"></a>

### NET.REQUEST_TYPE — CODE
Поле REQUEST_TYPE, NormalizeText. Только «предоставить доступ», «отозвать доступ», «предоставить», «отозвать» => PASS. MISSING => SKIPPED; EMPTY/другое => ERROR на поле, текст выбора двух типов. Внешних источников/допвыходов нет. Вектор «другое» => ERROR.

<a id="netsystem_iep"></a>

### NET.SYSTEM_IEP — CODE
Поле SYSTEM_IEP, NormalizeText. Только «да» PASS. MISSING => SKIPPED; EMPTY/«нет»/иное => ERROR на поле с указанием некорректной регистрации первой линией. Это сообщение касается первой линии, но окончательный recipient задаётся общим каталогом. Вектор «нет» => ERROR.

<a id="netvalidity"></a>

### NET.VALIDITY — CODE
Цель: срок доступа; REQUEST_TYPE + VALIDITY (Variant .Value первой ячейки). MISSING type => SKIPPED. Для «отозвать [доступ]» PASS без чтения срока; любой иной тип, включая INVALID/EMPTY, проходит ветвь срока, поэтому не следует считать условием лишь валидное предоставление. MISSING срока => SKIPPED; EMPTY => ERROR; NormalizeText «бессрочно» => PASS. Сначала IsDate/CDate; при неуспехе — regexp дат, последняя корректная дата из текста со строгой DateSerial roundtrip и годом 1900..9999. Ограничение года действует только в fallback; ранняя ветвь IsDate/CDate его не проверяет. Дата < Date => ERROR; текущая/будущая PASS; нераспознанное ERROR. Локаль IsDate и часы компьютера — зависимости. Адрес VALIDITY. Векторы: 31.02.2026 invalid; «с 01.10.2026 до 31/12/2026» => последняя дата. Встроен RunNetworkValidityDateRegression; выполнение не подтверждено.

<a id="nettop_justification"></a>

### NET.TOP_JUSTIFICATION — CODE
Поле TOP_JUSTIFICATION строка. MISSING => SKIPPED; EMPTY => WARNING на поле с пояснением, что исполнение не блокируется; любое непустое принято. Допвыходов/особого приоритета нет. Вектор пусто => WARNING.

<a id="nettechnical_table"></a>

### NET.TECHNICAL_TABLE — CONFIG
Верхняя таблица: TechnicalTableInfo, границы headerRow+1 .. lowerHeaderRow−1; source/destination/protocol/port/reason. Нераспознанная структура => SKIPPED. Строки без данных игнорируются; нет использованных строк => четыре ERROR на первом ряду (source,destination,protocol,port). Для каждой строки: source/destination EMPTY ERROR; неоднозначная запись ERROR и ранний выход парсера данной ячейки; invalid IP ERROR; текстовая группа в базовом main INFO; отсутствие любого распознанного элемента ERROR. Протокол EMPTY ERROR, иначе ParseTextTokens и NetworkProtocolCatalogText (Rulebook «Протоколы», fallback template.ini), неизвестные токены ERROR. Порт EMPTY ERROR; AnalyzeRequestPorts: диапазон 1..65535, invalid/no intervals ERROR. Пустое reason WARNING. Нормализованный текст четырёх основных полей образует ключ дубликата; последующая строка WARNING на source, UiGroup TECH_DUP|sheet|originalRow; reason в ключ не входит.

Integration активирует HotfixV3 → HotfixV2 → CheckNetworkTechnicalTable. Base integration поддерживает согласованный вертикальный merge как одну строку, собирает reason через mergeBottomRow. V2 удаляет legacy merge warnings, group INFO, ошибки пустых основных полей на служебных рядах и заново строит duplicate warnings; V3 удаляет ложные port errors при успешном AnalyzeRequestPortsCompat, где `/` и `\` заменяются на запятые. Не считать literal проблемы base окончательными: они могут быть удалены wrapper. Векторы: согласованный merge не даёт ложных дублей; `80/443` и `80\443` допустимы integration; `0` недопустим. Реальное оформление merge не проверялось.

<a id="netaddress_table"></a>

### NET.ADDRESS_TABLE — CONFIG
Нижняя таблица через AddressTableInfo и AddressTableLastDataRow; system,address,hostname,role. MISSING структуры SKIPPED; wholly-empty => WARNING system + ERROR address + ERROR hostname в первом ряду. Строка с любым значением: system EMPTY WARNING; address EMPTY ERROR; ambiguous ERROR с ранним выходом адресного парсера; invalid ERROR; группа main INFO, но сама по себе допустима; ничего распознанного ERROR. hostname EMPTY ERROR; role EMPTY WARNING. Integration dispatch Quiet hotfix: одинаковое MergeArea проверяется один раз на тип поля (SYSTEM/ADDRESS/HOSTNAME/ROLE); group INFO намеренно не создаётся. INVALID hostname синтаксически здесь не проверяется. Допвыходов нет. Вектор строка с system и пустыми остальными => две ERROR, role WARNING.

<a id="netaddress_match"></a>

### NET.ADDRESS_MATCH — CONFIG
Цель: сверка объявлений TOP↔LOWER, а не произвольная взаимозаменяемость сетей. Main safe wrapper: любое ambiguous IP в таблицах => SKIPPED. Любые текстовые группы => SKIPPED. Сверху нет объявлений => SKIPPED. Каждое нижнее объявление без верхнего => ERROR в каждой нижней ячейке; каждое верхнее без нижнего => ERROR в каждой верхней ячейке. INVALID IP сохраняется как INVALID|полный исходный текст. Ключ различает IP, CIDR, RANGE: IP и /32 различны; для CIDR сохраняется введённый base IP, не нормализованная сеть; full/short range эквивалентны; порядок/разделители не существенны.

Integration активен CompactCoverage: explicit IPv4 и explicit ranges сравниваются по фактическому покрытию; CIDR, включая /32, остаются строгими. При группах/ссылках переход в CoverageHotfix; auxiliary link рядом с распознанным IP не блокирует сверку, а даёт INFO NoCell ADDRESS_MATCH_LINKS. Это самостоятельный дополнительный result path того же RuleId. Coverage fallback разрешает нижние фактические IP внутри верхней сети; invalid объявления остаются строгими. Векторы: main `10.0.0.1-20` ↔ full range PASS; IP ↔ /32 ERROR; integration explicit range ↔ покрывающий список проверяется CompactCoverage, не main helper. Дополнительный outcome auxiliary links должен сохраниться отдельно от ошибок несовпадения.

<a id="netip_registry"></a>

### NET.IP_REGISTRY — CONFIG
Main dispatcher Safe → Intervals, а не legacy CheckNetworkIpRegistry. Ambiguous => SKIPPED; нет верхних интервалов => SKIPPED; нет подходящего Superset XLSX/индекс не построен => SKIPPED. Реальный matching — IPv4 interval intersection; не требуется полное покрытие запроса. Нет ни одного пересечения => WARNING «IP/сеть {displayText} не найдена в текущем файле выгрузки Superset. Требуется ручная проверка.» в каждой исходной ячейке; найдено => без issue. SOURCE:ТЕЛЕГРАФ / SOURCE: ЦХД / SOURCE: AWX индексируются как реальные адресные данные. Контекст поиска сохраняется даже при нуле совпадений; matchedEntries готовит lazy view, OpenMatchedRows=Yes.

Integration HotfixV2 → Hotfix расширяет поиск нижними адресами, в том числе отсутствующими сверху; lower-only missing даёт WARNING. V2 дополнительно объединяет TOP+LOWER для runtime-context и pending-view, не только предупреждений. Это дополнительный выход под прежним RuleId. View открывает временную копию, включает «AccessTools: IP из заявки»; narrowing hostname лишь при однозначной связи, fallback сохраняет IP matches. Coordinator/Superset enrichment — отдельные общие слои, не новые RuleId. Векторы: любой overlap => найдено, no overlap => WARNING; только нижний адрес тоже проверяется integration.

<a id="netip_exceptions"></a>

### NET.IP_EXCEPTIONS — CONFIG
Main Safe: ambiguous => SKIPPED. Integration ALLROWS wrapper вызывает напрямую CheckNetworkIpExceptions и этим не повторяет Safe gate; не переносить gate молча. Нет technicalRows/нет RULEBOOK/нечитаемый лист => SKIPPED; нет technical rules => PASS. «Правила и исключения» читается FlexCached. Заполненные IP/hostname/port/protocol/service условия работают AND; hostname связан через нижнюю таблицу, service через Superset контекст. При отсутствии service context или релевантных данных для подходящего кандидата WARNING «Сервисный контекст Rulebook» на вычисленном target. Runtime candidate matching, IP interval semantics и scope определяются общими helpers.

Для hostname-условий: Exact > StartsWith > Contains, затем длина; structured Service/Group только у максимальной специфичности. Конфликт одинаково специфичных structured результатов => ERROR «Конфликт Rulebook», structured output исключается, комментарии/согласования других matched правил остаются. Effective severity = максимум всех видимых displayRule для technical row и применяется ко всем опубликованным сообщениям этой строки. Дедуп severity|targetAddress|message локально строке. Target matched IP, иначе port если Port задан, иначе destination. Текст NetworkUnifiedRulePublicMessageV2.

Integration `ALLROWS:` в начале IP: output для совпавшего IP только когда все технические строки с этим IP в scope проходят остальные условия. Wrapper сначала вычисляет base, затем удаляет matching issues и пересчитывает counters. Поддерживает только IP/port/protocol; hostname/service исключены из AllRowsRuleSupported. При runtime error fallback сохраняет base results (не fail-closed). Вектор две строки одного IP 80 и 443, ALLROWS правило только 80 => не публиковать его результат. Actual workbook data/outputs не подтверждены.

<a id="nethostname_rules"></a>

### NET.HOSTNAME_RULES — CONFIG
Standalone hostname-only rules: AddressTableInfo; scan включает ширину merged hostname header, lastRow расширяется по фактическим hostname; каждое MergeArea единожды в пределах строки. MISSING структуры/нет hostname/нет файла/нечитаемый Rulebook => SKIPPED. HostnameRuleTokens: CR/LF/comma/pipe → `;`, NormalizeText, удаление завершающих точек, уникальные токены. Берутся только hostname rules без technical/service условий (комбинации обрабатывает IP_EXCEPTIONS). Приоритет/конфликт/максимальная severity аналогично карточке exceptions; более общие комментарии и approvals остаются. Дедуп severity|message на hostname, не глобально. Target исходное hostname MergeArea; конфликт ERROR там же. Нет matches => PASS. Вектор exact + contains: service/group exact, approvals обоих; конфликт двух exact => ERROR без произвольного выбора service.

<a id="netinitiator_ip_access"></a>

### NET.INITIATOR_IP_ACCESS — CONFIG
В main отсутствует. Feature/initiator-ip-policy имела 16 checks и прямой старый вход; integration использует Hotfix → Linked → base. Linked не даёт второму листу права допуска: если primary «Инициаторы» не разрешает email, либо email/file отсутствует/invalid, возвращает PASS без второго email issue; NET.INITIATOR_ALLOWED отвечает отдельно. Base без Linked для тех же причин возвращал SKIPPED. Источник RULEBOOK / «Ограничения IP инициаторов», активные selector + Scope + Allowed/DeniedIntervals + Comment. Не удалось загрузить/INVALID sheet => ERROR конфигурации; Linked очищает SheetName/Address таких ошибок, отвязывая от email. Пустой policies/нет совпадения => PASS/ALLOW только в отношении IP ограничений.

Точный email (2) полностью перекрывает домен (1); все строки лучшего score объединяются, НЕ исключает совпавший selector. Для SOURCE/DESTINATION объединяются применимые allowed и denied. Denied overlap имеет приоритет; если allowed nonempty — каждый интервал запроса должен быть полностью покрыт union allowed. Нет applicable policy/пустой request/no parsed intervals => без issue (invalid принадлежит technical check). Нарушение ERROR на source/destination: сообщение с email, введённым текстом, «Разрешено», «Запрещено (НЕ)», comments.

Hotfix отдельно проверяет lower-only интервалы, отсутствующие в upperIntervals, только для ANY/BOTH policy. Пропускает ambiguous/invalid нижние значения; одну физическую ячейку проверяет один раз. Нарушение ERROR на «Адрес» нижней таблицы, собственный текст «адрес … из нижней таблицы не разрешён политикой доступа». Это самостоятельный result path того же RuleId. Векторы: allowed /24 и request /23 => ERROR полного покрытия; deny пересекает => ERROR; нет IP-policy match => PASS при независимом primary allowed; lower-only вне ANY allowed => ERROR.

<a id="netinitiator_db_account"></a>

### NET.INITIATOR_DB_ACCOUNT — CONFIG
Только integration. Preconditions email найден, непуст, valid; RULEBOOK существует; primary allowed. Любой неудовлетворённый precondition => PASS без issue. EnsureNetworkInitiatorDbAccountColumn может добавить колонку «Учетная запись для портов БД» и dropdown в Rulebook, сохранить его, если открыт самой надстройкой и не ReadOnly; пользовательский открытый Rulebook не изменяется. Это дополнительный побочный эффект, не только read-only rule. DbAccountForbiddenForEmail выбирает общий best selector score (точный email выше домена), затем любой forbidden среди лучших запрещает. «запрещено/запрещен/запрещён/forbidden/deny/denied/нет/no» => запрет; empty/прочее => unrestricted. Отсутствие sheet/headers/ошибка чтения => False, следовательно PASS (не SKIPPED).

FindDbAccountField ищет anchor «Поля обязательные для портов БД», в его строке и следующих двух — метку учетной записи; поддерживает inline value и соседнее поле. MISSING target => PASS. Forbidden + непустой DbAccountFieldValue => ERROR на account: «Для данного инициатора запрещено указывать учетную запись для портов БД. Поле «Учетная запись» должно оставаться пустым.» EMPTY PASS. Условие фактического запроса DB-порта в entry function не проверяется: запрет привязан к наличию значения блока. Векторы: exact unrestricted перекрывает domain forbidden; один forbidden среди одинаково специфичных => ERROR при заполненном поле. Реальная приёмка не выполнена.

## Нормативные расхождения, требующие решения владельца

ТЗ v0.14 §7 фиксирует full IPv4 range как два явно названных адреса «пока аудит не подтвердит иное», CIDR по охвату и сокращённый список как будущее улучшение. Код interval parser, CompactCoverage и regression vectors уже имеют другую, контекстно различную семантику: диапазоны — интервалы, short ranges/list поддержаны; CIDR TOP↔LOWER строгий (включая base), registry/policy — по пересечению/покрытию. Нельзя вводить одну глобальную операцию «IP equals» и считать это parity. Требуется явное решение по каждому контексту, сохраняя code baseline до решения.

ТЗ v0.14 «нет правила инициатора => ALLOW» подтверждается для IP policy no match, но не для NET.INITIATOR_ALLOWED (есть активный список и нет match => ERROR), и не для unavailable source (SKIPPED в allowed, silent PASS в linked/DB). Разделять эти три ситуации обязательно.

ТЗ v0.13 описывает 15 текущих checks, но integration уже имеет 17 и wrappers. Число верхнеуровневых checks не равно числу бизнес-ветвей: service warning, conflict, group, merge, lower-only, auxiliary-link, ALLROWS suppression и source-unavailable — отдельные наблюдаемые outcomes.

Пустые строки и merged cells: main и integration не идентичны. Нет доказательства, что прохождение существующих regression макросов гарантирует реальные произвольные формы; ручная проверка остаётся UNVERIFIED.
