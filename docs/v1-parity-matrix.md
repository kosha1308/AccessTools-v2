# Матрица parity AccessTools 1 → AccessTools-v2

## Состояние

Это исходная спецификация сохранения поведения PR-00. Новая реализация правил отсутствует; все строки имеют статус **TODO v2**. Excel manual **не выполнен** для каждой строки; утверждение PASS по чтению кода не делается. 17 RuleId — только верхний уровень dispatch. [Реестр бизнес-ветвей](v1-business-rules.md) фиксирует дополнительные результаты, gates, подавления и legacy-входы под этими же RuleId.

Класс реализации: A — декларативная; B — составная; C — специализированная операция. Доказательства отдельно: CODE / CONFIG / UNVERIFIED. Существующий тест = процедура/сценарий найден в baseline, но в этой работе не запускался. Предлагаемый golden = требование к будущему parity fixture, не существующий тест и не результат выполнения.

## Источники против тестов против реального Excel

| Категория | Что проверено в PR-00 | Что не следует утверждать |
|---|---|---|
| Исходники | функции/dispatch/callsites прочитаны и связаны immutable ссылками; два baseline различаются | это не execution trace конкретной заявки |
| Existing VBA regression | найденные Run…Regression процедуры индексируются ниже | не запускались; READY/85 PASS из старой документации не воспроизводились |
| Proposed golden | таблицы выше задают положительные, отрицательные, empty/missing/invalid и output vectors | эти fixtures пока не написаны и не исполнены |
| Excel manual | не выполнен | UI, цвет, примечания, пользовательские notes/styles, lazy Superset и coordinator не приняты |
| Runtime Rulebook | формат и loader доказаны кодом | активные строки/публичные тексты/severity/audience пользователя не подтверждены |
| v2 | только документы, TODO | никакое правило не объявляется перенесённым |

## Нормативные решения перед реализацией

1. ТЗ14 §7 и код имеют разные контракты range/CIDR/short list; принять отдельное решение для TOP↔LOWER, Superset overlap, IP-policy full coverage, exceptions overlap. Сохранить code baseline до решения владельца.
2. Уточнить «нет правила → ALLOW»: разрешение подачи заявки, IP restriction no-match и unavailable source имеют разную фактическую семантику.
3. Зафиксировать integration как самостоятельный baseline и решить перенос каждого hotfix, включая тихие группы, port separators, merged rows и ALLROWS failure fallback.
4. Подготовить versioned Rulebook fixture с проблемами, routing, recipient, output texts и severity: исходный literal из check не равен окончательному сообщению.
5. Провести Excel manual по каждой строке с исходной копией заявки и снимком аннотаций/результатных книг до/после двух запусков. До этого подтверждение ручной приёмки UNVERIFIED.

## Связь классов C с операциями и общими выходами

Идентификаторы операций и подробные контракты следует сверять с [каталогом операций](operation-catalog.md), см. также [источники](v1-sources.md). Здесь описаны необходимые операции без присвоения неподтверждённых OperationId: strict date extraction (VALIDITY); IP/address/port/protocol parsing и merge-aware row traversal (TECHNICAL_TABLE/ADDRESS_TABLE); typed declaration + compact interval coverage (ADDRESS_MATCH); indexed registry overlap and lazy view context (IP_REGISTRY); unified AND matching, hostname specificity, service context, ALLROWS (IP_EXCEPTIONS); hostname specificity/conflict resolution (HOSTNAME_RULES); selector precedence + interval union/full coverage/deny overlap (INITIATOR_IP_ACCESS).

Для каждой строки матрицы конечные recipient, public/user/coordinator text и annotation addresses задаются общими каталогом проблем, routing, audience и writer после вычислительных targets, перечисленных в [индивидуальных карточках](v1-business-rules.md). Без versioned Rulebook fixture точные финальные тексты и recipients имеют статус CONFIG / UNVERIFIED; нельзя автоматически объявлять их одинаковыми для всех RuleId. Политика сохранности пользовательских примечаний и повторный запуск входят в общую ручную приёмку, не подтверждённую этим аудитом.

| RuleId класса C | Ярлыки специализированных операций каталога |
|---|---|
| NET.VALIDITY | C21 strict date extraction; OperationId не утверждён |
| NET.TECHNICAL_TABLE | C01, C02, C03, C05, C17; AnalyzeRequestPortsCompat — дополнение C03/C04 integration |
| NET.ADDRESS_TABLE | C01, C02, C17; quiet MergeArea traversal integration |
| NET.ADDRESS_MATCH | C01, C02, C16, C18; typed declarations, compact coverage и group/lower fallback |
| NET.IP_REGISTRY | C02, C08, C09, C18, C19, C20 |
| NET.IP_EXCEPTIONS | C02, C04, C05, C06, C09, C15, C17, C19; supported ALLROWS integration |
| NET.HOSTNAME_RULES | C06, C09, C19 |
| NET.INITIATOR_IP_ACCESS | C02, C07, C11, C12, C13, C14, C18; primary-linked policy + lower-only ANY/BOTH |

Общий результат всех классов проходит C10 метаданные и [контракт Excel-вывода](v1-excel-output-contract.md). Статус доказательств per-rule — CODE/CONFIG в карточках; status manual — UNVERIFIED во всех строках.



NET.INITIATOR_DB_ACCOUNT остаётся классом B (составная policy), использует C11/C14 для selector/eligibility и отдельный locator поля БД. Это не отсутствие специализированной зависимости.
